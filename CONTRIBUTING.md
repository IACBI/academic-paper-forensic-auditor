# Contributing

Contributions should make the review workflow clearer, more reliable or easier to use without claiming capabilities the project has not demonstrated. Start with the relevant part of the multilingual [README](README.md), then inspect nearby policy, schemas and tests before editing. Keep changes focused, explain the practical problem, and use synthetic examples that another maintainer can inspect safely.

## Maintain the right source

`master_prompt.md` is the canonical policy and standalone full protocol. The seven skill reference modules are generated by `scripts/build_references.py`; edit the master and regenerate them rather than maintaining parallel policies. Every numbered policy section must be routed exactly once. `SKILL.md` supplies entry-point routing and tool instructions, while its assets define the report and continuation contracts. `audit_tools.py` adds semantic checks that JSON Schema alone cannot express.

The README is the complete user guide in all 12 languages. Keep the language menu immediately below the title and maintain equivalent practical coverage in every language: purpose, setup, request settings, delivery formats, methods, report interpretation, confidentiality, continuation, optional tools and support. Detailed translations are intentional; reducing them to summaries or sending non-English readers to an English-only usage guide changes the documentation contract. Avoid redundant file trees, internal task history and unsupported marketing claims.

Keep the remaining documents purpose-specific. The [privacy guide](docs/PRIVACY.md) explains data handling, the [validation guide](docs/VALIDATION.md) records evidence and evaluation procedures, and the changelog records published changes. User-facing instructions belong in the README rather than a second usage manual. Runtime protocol resources, schemas, tests, fixtures and current acceptance baselines are functional project files, not disposable documentation copies.

`VERSION` contains the numeric version; display labels use `v.` before it. The manifest, skill metadata, schemas, helpers and examples must agree. Consider compatibility and migration before changing a structured contract. Keep provider-specific installation details optional, and select research checks by actual method, including unfamiliar or interdisciplinary approaches.

## Verify a change

Prompt use needs no Python environment. For development and optional helpers, use Python 3.10+ in an appropriate local environment, then run from the repository root:

```text
python -m pip install -r skills/academic-paper-audit/requirements.txt
python scripts/build_references.py
python scripts/check_project.py
```

The project check validates versions, reference synchronization, examples, source identity, schemas, current evaluation records, documentation file links and release inputs, then runs the behavior tests. The [CI workflow](.github/workflows/validate.yml) repeats the checks on Windows/Ubuntu and Python 3.10/3.14 and builds all distribution formats. Inspect any failure rather than skipping it or weakening an invariant to obtain a green result.

Add meaningful behavior tests when arithmetic, file boundaries, schemas, validators or packaging change. Documentation changes need editorial and link/structure checks; they do not need tests that merely duplicate exact wording. Review all 12 language sections when a user-facing capability changes. If the synthetic manuscript changes, recompute the example's artifact identity with the inventory helper, review its findings, and regenerate the checkpoint from the report. Updating a hash alone is not a substantive review.

Protocol, fixture or rubric changes can invalidate baseline snapshots. Before the project check, rerun the affected blind routes following [the evaluation procedure](docs/VALIDATION.md#prepare-a-blind-evaluation). A fresh responder receives the packet without expected answers; a separate judge inspects its actual output. Retain failures and uncertainty. Do not edit old response text, silently relax a criterion or change hashes to preserve a passing score. Scorer unit fixtures test the software and must not be reported as real scientific observations.

For unreleased work without fresh model access or expert review, retain original evaluated bytes in the release snapshot and validate old baselines explicitly as historical. State that current behavioral acceptance is pending; never substitute software tests for a new model evaluation. New robustness runs should use `--isolated` packets and distinct observed case-session IDs. The optional PDF tests require `requirements-pdf.txt`; CI runs them. README workflow markers allow command-coverage checks across 12 languages, not automatic translation certification.

## Prepare reviewable commits and releases

Use focused commits with clear purposes and inspect the staged diff before committing. Explain what changed, why it matters, what was checked and any remaining limits. Do not include real manuscripts, participant records, credentials or private findings. A minimal synthetic reproduction is preferable to a large unreviewable attachment. Do not create remotes, push or publish without owner authorization.

After the checks pass, build into a fresh output directory:

```text
python scripts/build_release.py --format all --output-dir dist/release
```

The default format without `--format` is the portable prompt package. Explicit `skill` and `plugin` formats target hosts that support them; an archive is not a universal installer. The allowlist excludes arbitrary files, evidence, private reports and development outputs. Existing outputs are preserved, so choose a new directory for a rebuild rather than overwriting material unintentionally.

Release notes should describe the actual contents, verified environments and evidence boundaries. Do not turn synthetic acceptance counts into detection rates or format checks into native-host certification. Published tags identify historical source snapshots; documentation updates on the main branch do not justify rewriting a released tag. Keep temporary packages and transport copies only as long as necessary, while preserving source, current tests and reviewed baseline evidence.
